# AGENTS.md

## Project

Programming Study Tracker is a personal web app for organizing programming study. The owner creates small goals under topics, logs what they did each week, and links the projects they built.

`plan.md` defines the scope, product rules, data model, screens, and build order. Read it before starting work.

**Current status:** The project switched from Supabase to Neon. Phases 1 to 7 are built locally on PGlite with a dev-only local owner; Neon, Neon Auth, and deployment are Phase 8. Topic, goal, settings, and auth components are prepared. Phases 1 and 2 (local foundation, topics and goals) are done; Phase 3 (weekly logs and projects) is next. See `plan.md` for verified progress.

## Stack

- Next.js 16 with the App Router and TypeScript in strict mode
- Tailwind CSS and shadcn/ui
- Drizzle ORM and drizzle-kit for queries and SQL migrations
- PGlite (embedded Postgres) for local development and tests
- Neon (Lakebase Postgres) and Neon Auth with GitHub login, connected in Phase 8 (`@neon/auth`, `@neondatabase/serverless`)
- Zod for input validation
- Vitest and Testing Library for unit and component tests
- Playwright for end-to-end tests
- npm as the package manager
- Vercel for hosting
- Node.js 22.13 or later (see `.nvmrc`)

Do not change the stack or add a major dependency without asking the owner.

## Commands

```bash
npm run dev                  # Start the app locally (local owner mode, PGlite)
npm run lint                 # Run ESLint
npm run typecheck            # Run tsc --noEmit
npm test                     # Run unit, component, and database tests
npm run test:e2e             # Run Playwright tests
npm run build                # Create a production build

npm run db:generate          # Generate a migration from src/db/schema.ts
npm run db:generate -- --custom --name <name>   # Empty SQL migration for triggers and functions
npm run db:migrate           # Apply migrations to the local PGlite database
npm run db:reset             # Delete and rebuild the local PGlite database
```

Neon commands (`neon link`, `neon checkout`, `neon deploy`) are used from Phase 8 only.

## Project structure

```text
src/
  app/                  Routes, layouts, and Route Handlers
  components/ui/        Shared shadcn/ui components
  features/<feature>/
    actions.ts          Server Actions ("use server"; form actions only)
    queries.ts          Server-side reads that take a UserScope
    mutations.ts        Server-side writes that take a UserScope
    schemas.ts          Zod schemas
    components/         Feature components
    *.test.ts(x)        Tests beside the code they cover
  db/
    schema.ts           Drizzle schema (source of truth for tables)
    client.ts           Server-only database client (PGlite now, Neon in Phase 8)
    test-database.ts    Fresh in-memory database for tests
  lib/auth/             requireUser() and session helpers
  lib/dates/            Week and date helpers
  lib/github/           GitHub API client
  proxy.ts              Login redirects (Phase 8)
drizzle/                SQL migrations generated by drizzle-kit, plus custom SQL
tests/e2e/              Playwright tests
```

## Coding rules

- Before Next.js work, read the relevant guide in `node_modules/next/dist/docs/`. Do not rely on memory for framework APIs.
- Use `proxy.ts`, not `middleware.ts`.
- Use Server Components by default. Add `"use client"` only when a component needs browser interactivity.
- Read data in `queries.ts` and write it in `mutations.ts`. Both take a `UserScope` (`{ db, userId }`) from `requireScope()`. Server Actions in `actions.ts` validate input, call `requireScope()`, and then call a mutation.
- Never export a function that accepts a user ID or scope from a `"use server"` file. Every export there is a public endpoint that the browser can call with any arguments.
- Use Route Handlers only when a URL endpoint is required, such as the OAuth callback.
- Validate every Server Action input with Zod, on the server, even if the form already validated it.
- Return `{ ok: true, data }` or `{ ok: false, error }` from Server Actions for expected failures.
- Revalidate the affected routes after a successful change.
- Do not use `any`. Use the types inferred from the Drizzle schema (`$inferSelect`, `$inferInsert`).
- Use kebab-case for file names and PascalCase for React components.
- Use the helpers in `src/lib/dates` for week calculations.
- Store activity dates as PostgreSQL `date` values, not timestamps.
- Give every form visible labels, validation messages, and a pending state.
- Give every list an empty state.
- Make all features usable with a keyboard. Do not use color as the only signal.

## Security rules

- `proxy.ts` is not enough to protect the app. Call `requireUser()` in every protected page, query, and Server Action.
- Take `user_id` only from `requireUser()`. Never accept it from the browser.
- Filter every owned-table query by that `user_id`, including updates and deletes. Put the filter inside shared select helpers so callers cannot leave it out. A missing filter is a security bug.
- Import the database client only from server code. Mark data modules with `import "server-only"`.
- Never send a database URL, cookie secret, or token to the browser. Never prefix them with `NEXT_PUBLIC_`.
- The local owner must work only when `NODE_ENV` is `development`, `LOCAL_OWNER_MODE=1`, and `VERCEL` is unset. It must fail closed everywhere else. Never add another login bypass.
- From Phase 8, read sessions with Neon Auth's server `auth.getSession()` and allow only users in `ALLOWED_USER_IDS`.
- Keep secrets in `.env.local` and Vercel environment variables. Never commit them.
- Keep `.env.example` in Git with placeholder values only.
- `GITHUB_TOKEN` must stay on the server.
- Allow only `https` URLs for repositories, live sites, and resources.
- Never show private study data on the public portfolio page. See section 8 of `plan.md`.

## Database rules

- Define tables in `src/db/schema.ts` and generate migrations with drizzle-kit. Put triggers and functions in custom SQL migrations.
- Never edit a migration that has been committed or applied outside your local database. Add a new one.
- Give every owned table a `user_id` column that references `profiles.user_id`.
- Use composite foreign keys so a row can reference only rows owned by the same user.
- Enforce rules that must not be bypassed (limits, status transitions, archive rules) in the database as well as in server code. Raise custom SQLSTATE codes from triggers and list them in `src/lib/db/errors.ts`.
- Create views with `security_invoker = true`.
- Set a fixed `search_path` on every function, and on every `SECURITY DEFINER` function.
- Store activity dates as PostgreSQL `date` values, not timestamps.
- Apply migrations to Neon only in Phase 8, and to production only with the owner's approval.

## Scope limits

Do not build these features:

- Weekly reflection prompts, including "What did I learn?", "What confused me?", and "What's my next step?"
- AI quizzes or any other AI feature
- Team, social, or payment features
- Native mobile apps

Add new ideas to "Ideas for later" in `plan.md` instead of building them.

## Workflow

- Follow the phases in `plan.md` in order, one task at a time.
- Tick a task only after you have verified it.
- Record important decisions in the decision log in `plan.md`.
- Use small commits with Conventional Commit prefixes: `feat:`, `fix:`, `test:`, `docs:`, and `chore:`.
- Ask the owner when a requirement is unclear and the wrong choice would be hard to reverse.

Get the owner's approval before you:

- Deploy to production
- Change a production database
- Delete data
- Add a paid service
- Change the stack
- Force-push to a shared branch

## Before finishing a task

Run these checks:

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Also complete the checks that apply to your change:

- **UI change:** Test it in a browser at desktop and mobile widths.
- **Schema change:** Run `npm run db:reset` and the database tests in `npm test`.
- **New table:** Add an ownership test proving that one user cannot read or change another user's rows.
- **Main user flow change:** Run `npm run test:e2e`.

Finish by reporting what changed, what you tested, and anything that remains unfinished.
